## 0. Codexへの指示の読み方
このドキュメントはAIコーディングエージェント（Codex）に渡す実装プロンプトです。上から順に「背景→差別化方針→MVP機能→データ→技術構成→画面→実装ステップ→制約」の順で記載しています。まず全体を読んでから実装計画（TODOリスト）を提示し、私の承認を得てからコードを書き始めてください。

**不明点の扱い方**：不明点があっても、実装計画の作成段階では合理的な仮定を置いて提案すること。軽微な不明点ごとに質問を返さず、重大な技術的制約（実装がそもそも成立しない等）や有償サービスの利用が必要になる場合のみ、確認事項として列挙すること。

## 1. 背景・コンテキスト

- 東京都主催「都知事杯オープンデータ・ハッカソン2026」への提出作品を作る
- 2026年テーマ：「オープンデータ×生成AI」
- 開発環境：OpenCode（生成AI開発ツール）＋ Cloudflareの有償プラン相当環境（無償提供、9月末まで）
- 実装エージェント：Codex

### 審査傾向（重要・設計方針に反映すること）
- 2024・2025年と2年連続で「防災・安全・気候リスクの可視化」が最優秀賞を獲得（熱中症リスクマップ、夜道安全"YORUMICHI"）
- 複数のオープンデータを掛け合わせて新しい価値を出すこと、地図・スコア化などの視覚的インパクトが評価されやすい
- → 本提案でも「単一データの表示」で終わらせず、**複数データセットの掛け合わせ**と**視覚的にわかりやすいスコア/マップ表現**を必須要件とする

### 課題設定
- クーリングシェルター（避暑施設）は場所・定員データは東京都からオープンデータとして公開されているが、**リアルタイムの空き状況データが存在しない**
- 既存の類似サービスとして、NAVITIME「ALKOO」が建物ベースの日陰ルート＋クーリングシェルター表示を商用提供済み。**そのまま同じものを作ると差別化できない**

---

## 2. 差別化方針（Codexは実装時に必ずこの3点を意識すること）

1. **街路樹の緑陰データの活用**
   東京都の街路樹オープンデータ（樹種・位置・場合により樹高情報）を使い、建物の日陰だけでなくルート沿いの並木・緑陰を考慮した「涼しい経路」を提案する。ALKOOは建物日陰ベースなので、街路樹データの活用はここでの独自性になる。

2. **低コストな空き状況の可視化の仕組み**
   リアルタイムの混雑センサーは前提にしない。施設スタッフが簡単に更新できる低コストな更新手段（例：Web簡易フォーム／LINE風の1タップ更新UI）を用意し、「空き・やや混雑・満員」程度の粗い3段階ステータスを地図上に表示する。ハッカソンのデモでは、この更新UIと反映結果をセットで見せることが評価ポイントになる。

3. **特定ユーザー層への特化**
   全ユーザー向けの汎用アプリではなく、高齢者・子ども連れ・屋外作業者など熱中症リスクが高い層を想定ペルソナとして明示し、UIやルート提案のロジック（休憩スポット頻度、歩行速度想定など）に反映する。
   デザインは、行政の堅い雰囲気にならないよう**モダンなUI**を基本方針とする（対象ペルソナへの配慮は文言・情報の出し方・提案ロジック側で行い、見た目のトーン自体は洗練されたモダンさを優先する）。

## 3. MVP機能要件

### 3.1 必須機能（デモで必ず動かす）
1. **地図表示**：クーリングシェルター一覧を地図上にピン表示（東京都オープンデータ）
2. **表示エリアモードの手動切り替え**：「現在地モード」と「デモ保証エリアモード（江東区）」をユーザー（発表者）が明示的に切り替えられるトグルを用意する
   - 自動判定によるエリア切り替えは行わない（判定ロジックの誤作動によるデモ事故を避けるため）
   - デモ保証エリア（江東区）は、クーリングシェルター・街路樹・公園・給水スポットの4データが揃っていることを確認済みのエリアとし、審査本番はこちらを基本に使う想定とする
   - 現在地モードでシェルターが0件など、表示に必要なデータが極端に少ない場合は、地図上に「このエリアはデータが少ない可能性があります。デモ対応エリア（江東区）もお試しください」という案内バナーを表示する（自動切り替えはせず、案内のみに留める）
3. **涼しいルート提案**：出発地はGPS現在地を基本とする。目的地は**クーリングシェルターに限定せず、任意の場所を指定できる**ようにし、指定方法は「住所・地名検索」と「地図タップ」の両方に対応する。指定すると、街路樹データを加味した経路を提案し、通常最短経路と並べて比較表示する
   - 検索には無料のジオコーディングAPI（例：Nominatim等）を利用する
   - シェルターを目的地にしたい場合は、従来どおり施設詳細画面の「ここへ向かう」ボタンから直接遷移できるようにする（3.1の他機能との整合を保つ）
   - 差別化維持の観点：目的地を自由化してもNAVITIME「ALKOO」との違いが薄れないよう、街路樹データによる涼しさスコアと空き状況の可視化を常に前面に出す（6.4の理由カード等）
4. **休憩スポット統合表示**：提案ルート沿いに加え、目的地周辺のシェルター・公園・給水スポット等もマーキング表示する。公園は日陰の多い公園（緑陰の多い樹木データが確認できる公園）のみを対象とする
5. **空き状況の簡易更新・表示**：
   - 施設スタッフ用：3段階（空き／やや混雑／満員）をワンタップで更新できる簡易画面（認証は簡易でよい。デモ用に施設IDベースのURLでも可）
   - 利用者用：地図上のピンの色で空き状況を表示
6. **熱中症リスクの可視化**：気象データ（気温・WBGT等、取得可能なオープンデータ/APIがあれば使用）と組み合わせ、選択中エリア（現在地モード／デモ保証エリアモード）周辺のリスクレベルをスコア表示

### 3.2 あると良い機能（時間があれば）
- 想定ペルソナ切り替え（高齢者モード／子ども連れモード等でルート提案パラメータを変更）
- 過去の更新履歴からの混雑傾向の簡易予測（本格的な予測モデルは不要、曜日・時間帯の単純集計で可）

### 3.3 「涼しいルート」のMVP算出方針（重要：独自ルーティングエンジンは作らない）
本MVPでは、独自の道路ネットワーク探索アルゴリズムは実装しない。既存のルートAPIの結果を活用したスコアリングに徹すること。

- ルートAPIから複数候補ルートを取得できる場合、その候補同士を比較する
- 各ルート周辺一定距離内に存在する街路樹数・公園・給水スポット数を集計する
- 距離・所要時間・街路樹密度・休憩スポット数から「涼しさスコア」を算出し、最もスコアが高い候補を「涼しいルート」として表示する

**涼しさスコアの初期案（0〜100点、係数は設定ファイルに切り出し後から調整可能にする）**
- ルート周辺の街路樹密度：40%
- 緑陰公園の有無：20%
- 給水・休憩スポット数：20%
- 最短ルートに対する追加時間の少なさ：20%

算出根拠は画面に表示する（6.4「理由カード」参照）。なお実データだけでは正確な「街路樹カバー率」を計算しきれない場合があるため、指標名は「ルート周辺の街路樹密度」または「緑陰スコア」といった表現にとどめ、精度を保証するような言い回しは避けること。

## 4. データソース候補（Codexは実装前に実際のURL・データ構造を確認すること）

| データ | 想定ソース | 用途 |
|---|---|---|
| クーリングシェルター一覧（施設名・住所・定員） | 東京都オープンデータカタログサイト | 基本の地図表示 |
| 街路樹データ（樹種・位置） | 東京都オープンデータ（区市町村単位の場合あり） | 緑陰ルート算出 |
| 気温／WBGT等の気象データ | 気象庁API・環境省熱中症予防情報サイト等 | リスクスコア表示 |
| 公園・給水スポット等 | 東京都・各区市町村オープンデータ | 休憩スポット表示 |
| 地図タイル | OpenStreetMap | 地図表示（Leaflet、5章参照） |
| ルート探索 | OpenRouteService（Directions API） | 涼しいルート提案（5章参照） |
| 住所・地名検索（ジオコーディング） | Nominatim（OpenStreetMap）等 | 目的地検索（5章参照） |

※ 有償APIを使う場合はハッカソン期間中の無料枠内に収めること。GPS取得自体はHTML5 Geolocation APIで無償。

## 5. 技術構成（提案・Codexが妥当と判断すれば変更可）

- フロントエンド第一候補：**React + TypeScript + Vite**
  - UI：Tailwind CSS
  - 地図：Leaflet + OpenStreetMap
  - アイコン：Lucide React等の軽量ライブラリ
  - 状態管理：React標準の useState/useContext を基本とし、MVPでは大規模な状態管理ライブラリを導入しない
  - （Cloudflareとの相性・MVPの軽さを優先し、上記を第一候補とする。Codexが別構成を強く推奨する場合は理由とともに提案してよい）
- ルートAPI：**OpenRouteService（Directions API）**
  - プロファイル：foot-walking（徒歩）
  - `alternative_routes` オプションで複数の候補ルートを取得し、3.3節の涼しさスコアで比較・選定する
  - 無料枠（1日2,500リクエスト・月40,000リクエスト）の範囲で開発・デモを行う。APIキーが必要
  - 取得したルート形状（ポリライン）に対し、街路樹・公園・給水スポット等のオープンデータをバッファ範囲でカウントする処理は自前実装する（turf.js等の利用を想定）
  - レート制限超過・API失敗時は、最短ルートのみの表示等にフォールバックし、アプリ全体を止めない
- ジオコーディングAPI：**Nominatim（OpenStreetMap）等の無料サービス**
  - 目的地の住所・地名検索（3.1「涼しいルート提案」の検索指定に使用）
  - 利用ポリシー上のレート制限（過度な連続リクエスト不可等）に留意し、検索は入力確定時のみ呼び出す設計とする（キー入力ごとの逐次呼び出しはしない）
- バックエンド：Cloudflare Workers等、提供環境に準拠した軽量API
- データ保存：空き状況の更新値など、軽量なKVストア/DBで十分（本格的なRDB設計は不要）
- 生成AIの用途とフォールバック方針：
  - 生成AIは**ルート算出そのものには使用しない**。用途は以下に限定する
    - オープンデータのラベル・粒度が異なる複数データセットの名寄せ・統合（住所表記ゆれの吸収等）
    - 算出済みスコア（涼しさスコア・熱中症リスクスコア等）を根拠に、説明文を自然文生成する
    - ペルソナ別のルート提案理由をテキストで自然文生成する
  - APIキー未設定時・生成AI API呼び出し失敗時は、**テンプレート文による説明表示にフォールバック**し、主要機能（地図表示・ルート比較・空き状況表示等）を停止させない設計とする

## 6. 画面構成（詳細）

### 6.0 共通UI方針
- スマートフォンファーストで実装する
- 基準画面幅は390px程度とする。PC表示では最大幅480px程度のスマホUIを中央配置してもよい
- 地図はトップ画面・ルート画面ともに画面の50%以上を占める
- 主要ボタンのタップ領域は最低44px以上とする
- 角丸カード、控えめな影、十分な余白を用いたモダンなデザインとする（2章の「モダンなUI」方針と一致させる）

**地図上の色ルール（色の意味の重複を避けるため厳守すること。色だけでなくアイコン形状・ラベルでも状態を判別できるようにする）**
| 対象 | 色 |
|---|---|
| シェルター：空き | 青 |
| シェルター：やや混雑 | 黄 |
| シェルター：満員 | グレー |
| 緑陰の多い公園 | 緑 |
| 給水スポット | 水色 |
| 涼しいルート | 濃い緑の実線 |
| 最短ルート | 濃いグレーの破線 |

### 6.1 画面遷移の全体像
トップ画面（地図）を起点に、①シェルターをタップ→施設詳細→ルート提案、②検索/地図タップで直接目的地指定→ルート提案、の2つの導線を持つ。施設スタッフ用更新画面は一般利用者の動線とは切り離した別入口（施設IDベースのURL等）とする。

```
トップ画面（地図）
  ├─ シェルターのピンをタップ → 施設詳細画面
  │      └─ 「ここへ向かう」ボタン → ルート提案画面（目的地＝そのシェルター）
  ├─ 検索ボックスに住所・地名を入力、または地図タップ → ルート提案画面（目的地＝指定した場所）
  └─ ヘッダーの熱中症リスクスコア → タップで簡易説明を表示（モーダル/ドロワー）

施設スタッフ用更新画面（別入口・一般動線から独立）
```

### 6.2 トップ画面（地図）
- **エリアモード切り替え**：「現在地モード」「デモ保証エリア（江東区）モード」を切り替えるトグルをヘッダー上部に常設する（自動判定は行わない。3.1参照）
- **目的地検索ボックス**：地図上部に検索ボックスを常設し、住所・地名を入力するとルート提案画面へ遷移する（目的地＝検索結果の場所）。地図タップでも同様にルート提案画面へ遷移できる
- **地図エリア**：選択中モードの中心地点を基準に表示。クーリングシェルターのピンを空き状況の3段階（空き＝青／やや混雑＝黄／満員＝グレー、色ルールは6.0参照）で色分け表示
- **上部ヘッダー**：選択中エリア周辺の熱中症リスクスコア（数値＋アイコン、例：注意/警戒/危険の3〜4段階）。タップでWBGT等の根拠データを簡易表示
- **フィルタ／ペルソナ切替**（あると良い機能）：高齢者モード／子ども連れモード等の切り替えボタンをヘッダー下に配置
- **凡例**：ピンの色の意味（空き状況）と、緑陰の多い公園を示すアイコンの凡例をマップ下部に小さく表示
- **データ不足時の案内バナー**：現在地モードでシェルター件数が極端に少ない（例：0件）場合、地図上部に「このエリアはデータが少ない可能性があります。デモ対応エリア（江東区）もお試しください」というバナーを表示する。自動でのモード切り替えは行わない
- 空データ・GPS取得失敗時は、位置情報の許可を促すメッセージ＋東京都心のデフォルト表示にフォールバックする

### 6.3 施設詳細画面
- シェルターのピンをタップした際にボトムシート（またはモーダル）で表示
- 表示項目：施設名、住所、定員、現在の空き状況（3段階＋最終更新時刻）、開放可能日時
- 主要CTA：「ここへ向かう（涼しいルートを見る）」ボタン → ルート提案画面へ遷移
- 最終更新時刻が一定時間（例：3時間等、実装時に決定）を超えている場合は「情報が古い可能性があります」の注記を表示する

### 6.4 ルート提案画面
- 上部：地図上に「涼しいルート」「最短ルート」の2本を色分け表示（涼しいルート＝濃い緑の実線、最短ルート＝濃いグレーの破線、色ルールは6.0参照）
- 下部または横に比較パネルを表示：所要時間・距離・ルート周辺の街路樹密度（緑陰スコア）を2ルートで並べて比較
- **「このルートがおすすめの理由」カード**を比較パネルの下に表示する（審査員に、複数のオープンデータを掛け合わせた結果であることを一目で伝えるための要素）
  - 表示例：「最短ルートより2分長い」「ルート周辺の街路樹が約1.6倍」「緑陰公園を1か所経由」「給水スポットが2か所」
  - 生成AIが利用可能な場合はこれらの数値を基に自然文で説明を生成し、失敗時はテンプレート文（上記のような箇条書き）にフォールバックする
- ルート沿い＋目的地周辺の休憩スポット（公園・給水スポット等）をアイコンでマップ上に表示。タップで簡易情報を表示
- 出発地はGPS現在地固定。目的地はトップ画面（検索または地図タップ）もしくは施設詳細画面（「ここへ向かう」）から引き継がれた状態でこの画面に遷移する。この画面単体での目的地の再指定は必須ではないが、地図タップでの再指定を許容してもよい
- 「涼しいルートで案内開始」ボタンは、ハッカソンMVP範囲では外部地図アプリへのディープリンク（ナビ機能そのものは自前実装しない）でも可

### 6.5 施設スタッフ用更新画面
- 施設IDベースの専用URL等でアクセス（一般利用者の動線からは非表示）
- 画面はシンプルな1画面構成：現在の空き状況を3つの大きなボタン（空き／やや混雑／満員）から選択してワンタップ更新
- 更新後は「更新しました（最終更新：HH:MM）」を明示するトースト/バナー表示
- モダンなUIトーンは維持しつつ、施設スタッフが忙しい中でも迷わず使えるよう、文字サイズ・タップ領域を大きめにする

## 7. 実装ステップ（Codexへの進め方の指示）

1. まずオープンデータの実データ構造を確認し、データ取得・パース方針を提示する
2. 地図表示＋シェルターピン表示のMVPを最初に動かす（ここが動けば最低限のデモが成立する）
3. 空き状況の更新・反映の一連の流れ（スタッフ更新→利用者表示）を実装する
4. 街路樹データを使った涼しいルート提案ロジックを実装する（データが揃わない区市町村がある場合は、対象エリアを絞ってでも良いので確実に動くデモにする）
5. 熱中症リスクスコア表示、ペルソナ切り替え等の付加機能は最後に着手する
6. 各ステップ完了時に動作確認できる状態を保つ（一気に全部作らず、動くものを積み上げる）

実装を進める中で**実際にコードに組み込んだ**オープンデータを、Codexは実装と並行してリポジトリ内に記録し続けること。プレゼン資料にそのまま転記できる状態を常に維持する。

- 記録先：`docs/USED_OPEN_DATA.md`（新規作成）
- 記録タイミング：候補として検討した時点ではなく、**実際にコードから取得・参照するようになった時点**で追記する（未使用のまま終わった候補データは載せない）
- 記録は以下の2種類に**分けて**記載する（「オープンデータ活用」の説明で混同しないため）：
  1. **オープンデータ**（東京都・気象庁等の行政・公的機関が公開するデータ）
     | データ名 | 提供元 | URL | 実装箇所（ファイル/機能） | 用途 |
  2. **利用API/サービス**（OpenRouteService、Nominatim等、OSMベースの第三者サービス。オープンデータそのものではなく、それを加工・提供するサービス）
     | サービス名 | 提供元 | URL | 実装箇所（ファイル/機能） | 用途 |
- モックデータで代替した項目についても、「本来接続する予定のオープンデータ」として1のオープンデータ表に区別して記載する（列を分けるか、備考欄に「※モック代替」と明記）
- 実装ステップ（7章）の各ステップ完了時に、その時点で組み込んだデータ・サービスをこの記録に反映すること
- 最終的にこのファイルの内容が、そのままハッカソンのプレゼン資料の「使用データ」スライドの元データになる（発表時は1のオープンデータ表を主役として説明し、2は技術構成の補足として扱う）

## 9. 制約・注意事項

- ハッカソンのデモ時間内で説明・動作確認できるシンプルさを優先する。過剰な機能追加より、差別化3点（街路樹データ／空き状況可視化／特定層特化）が明確に伝わることを優先する
- 実データが取得できない項目はモックデータで良いが、「本来はこのオープンデータを使う」という接続方針をコード内コメント・READMEに明記する
- NAVITIME「ALKOO」等の既存サービスと重複する機能（建物日陰ベースのルートのみ等）は主機能にしない
